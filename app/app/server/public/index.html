为什么会 Permission denied

      
Linux 的普通权限由属主 UID、属组 GID 和权限位决定；飞牛 NAS 还会在 POSIX ACL 中记录用户、用户组、掩码和默认 ACL，共享目录通常使用继承 ACL 控制访问。Docker 绑定挂载只是把 NAS 目录映射到容器路径，不会把目录复制到容器里，也不会重写这些权限。

      
容器里的进程仍有一个宿主机视角的 UID/GID。容器内的路径访问最终由 Linux 内核按挂载在 NAS 上的真实文件判断：先看文件属主和权限位，再看 POSIX ACL、补充组和用户映射。Docker 镜像经常使用固定 UID，如 999、1000、1001；飞牛共享目录又可能由管理员账户或继承 ACL 管理。当两者不一致，而容器进程又不在允许访问的用户组里，读文件、写文件或进入目录就会被内核拒绝，容器日志通常显示 Permission denied。

      
常见场景包括：镜像用固定 UID/GID，但目录被飞牛用户或应用 UID 占有；Compose 设置了 user，但目录没有对齐到这个 UID/GID；共享目录的 ACL 掩码或拒绝项没有给容器进程对应身份；目录权限是 700 或 750，其他身份无法进入；挂载被设为只读但容器仍尝试写入；容器启用用户映射或 rootless 时，容器内身份与宿主机 UID 不同。属主不同不一定会失败，关键取决于容器实际需要读、写还是进入。

    

    
本应用做什么

      
应用扫描 Docker 明确映射到宿主机的目录或文件，检查容器实际身份能否访问这些路径。它只处理绑定挂载的挂载路径本身，不递归扫描子文件；只读挂载不要求写入。

      
修复时把挂载路径属主对齐到容器 UID/GID，再补齐业务所需的读、写或进入权限，保留 ACL。修复可以直接执行，不需要先停止容器；完成后建议重启容器并结合业务日志确认效果。

      
应用不自动停止或启动容器，不设置 777，不修改 Compose，不处理命名卷、系统目录、Docker 引擎内部目录、共享重叠路径、链接、硬链接文件和不支持的文件系统。

    

    
检查原理

      
应用从 Docker inspect 获取绑定挂载路径和容器身份，再从宿主机 /proc 中读取容器工作进程的 UID/GID、补充组和身份映射。随后以该身份模拟访问挂载路径，判断读、写、进入是否满足需求。

      
结果只表示挂载路径在已检查范围内的访问能力，不代表容器内全部运行环境。无法核实身份、容器已停止或本次未执行检查时显示“未检测”；不能把“未检测”当作正常或异常。

    

    
应用侧操作

      
    
        
  1. 点击“开始扫描”。左侧目录树会列出 Docker 项目和容器，右侧显示检查结果。
    2. 
        
  2. 点击项目或容器跳转；点击顶部“正常 / 需关注 / 未检测 / 检测失败”状态卡筛选列表，再次点击同一状态卡恢复全部状态。
    3. 
        
  3. 展开“查看诊断与范围”，确认路径、容器身份、当前属主和受限操作。
    4. 
        
  4. 勾选可修复项，点击“批量修复选中项”预览变更。确认窗口会列出路径和修改前后的属主、权限。
    5. 
        
  5. 确认执行后，修复结果显示在“检查与修复”下方，可点击“收起”。请重启对应容器并结合业务日志确认效果。
    6. 
        
  6. 修复后可重新扫描验证最新权限状态。“更多操作”支持导出诊断和查看审计。
    7. 
      

    

    
四种结果状态
正常
挂载路径在已检查范围内访问通过。属主不同本身不表示权限错误。
需关注
挂载路径存在访问限制或路径问题；只读配置不可写可能正常，不等于容器启动故障。
未检测
容器已停止、身份无法模拟，或本次未执行访问检查；没有绑定挂载的容器也计入此项。
检测失败
检测执行发生错误，需查看原因后重新扫描。
项目、容器显示其中最需要关注的状态；左侧始终保留所有项目，点击跳转会清除右侧筛选。

    
修复边界

      
修复期间请勿重启、重建或修改对应容器，否则应用会拒绝继续执行并提示重新预览。执行前会重新核对容器配置、挂载路径和运行身份。缺少 getfacl 时禁用修复；调整普通文件属主前还会检查 getcap。

      
每批最多 100 个挂载路径。修改记录保留权限和 ACL 信息，可用于排查，但不包含文件内容，不是业务备份。
