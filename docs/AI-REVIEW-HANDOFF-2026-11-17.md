## 4 修复范围与文件系统安全

### SAFE-01 P0 系统路径保护只匹配少数目录本身

- 状态：函数已复现；误修改后果未在真实目录试验。
- 位置：引擎 `is_protected_path`，第 39–44 行；scan 和 fix 均使用它。
- 问题：保护 `/etc` 不保护 `/etc/ssh`；保护 `/var/lib/docker` 不保护其子目录。也没有禁止 NAS 卷根、系统管理目录、应用自身及 Docker 实际 data-root。
- 修改：统一规范化路径边界校验；按目录组件匹配系统子树；运行时发现 Docker data-root 与 NAS 管理路径；明确拒绝卷根本身。避免粗暴禁止所有 `/vol1/*`，否则会挡住正常项目目录。
- 验收：扫描与修复共用同一规则；系统子树、卷根、应用与 Docker 管理数据路径无法进入可执行计划；相似前缀 `/etc-backup` 不被错误匹配为 `/etc`。

### SAFE-02 P0 共享识别漏掉父子路径和同一目录的别名

- 状态：代码确认。
- 位置：引擎第 188–190、260–262、391–395、433–439 行的 `SRC_COUNT`。
- 问题：只统计规范路径完全相等。容器 A 挂 `/project`，容器 B 挂 `/project/db` 时，修复 A 会改动 B。不同路径的 bind 别名也可能指向同一对象。相反，同一容器多次引用同一路径一律算共享，属于保守但未清楚说明的限制。
- 修改：检测规范路径相等、祖先和后代重叠；必要时结合设备/inode 和 mount 信息。把冲突容器和挂载列入结果；无法证明独占时拒绝递归修复。
- 验收：相等、父子、别名、停止容器、身份未知容器、同容器重复引用分别有测试；`/data/a` 与 `/data/ab` 不应算父子。

### SAFE-03 P0 扫描与修复跨挂载边界的策略不一致

- 状态：代码确认。
- 位置：扫描 `find -xdev` 第 289、320 行；修复第 445–462 行。
- 问题：扫描限制设备边界，清 ACL、`chown -R` 和修复阶段的 find 没有同样限制。源目录下的独立文件系统可能未被完整检测却被递归修改。同设备 bind 子挂载也不能单靠 `-xdev` 排除。
- 修改：预检 mountinfo，明确受控的遍历范围；检测到嵌套挂载时默认拒绝或按明确的子计划处理。所有修改阶段使用同一受验证对象集合，不能只给某一个 find 加参数。
- 验收：目录下挂入临时独立文件系统和同设备 bind mount，范围外元数据保持不变；界面说明被排除范围。

### SAFE-04 P1 路径检查与使用之间存在变化窗口

- 状态：代码确认；利用条件待 Linux 验证。
- 位置：fix 第 403–411 行建图，之后第 444–462 行使用保存的字符串路径。
- 问题：建图后容器或其他进程可替换目录、符号链接或内部文件。初次 `readlink -f` 不能保证后续每次操作仍指向原对象；硬链接还会使目录外同一 inode 的元数据一起变化。
- 修改：记录并复核设备、inode、挂载和规范路径；明确链接策略，对多链接文件保守处理；评估基于目录句柄和不跟随链接的操作。无法可靠防护的情况应阻断自动递归修复。
- 验收：受控样本中替换源目录或内部路径，操作应拒绝或停止；范围外对象不得改变。不要未经验证就声称 GNU `chown -R` 一定跟随所有符号链接，具体语义需按目标工具核实。

### SAFE-05 P1 旧指纹没有绑定用户确认的修复计划

- 状态：代码确认。
- 位置：`fingerprint` 第 115–117 行；fix 第 398–410 行；后端第 117–134 行。
- 问题：key 仅为容器名和规范路径的可预测 SHA256。扫描后同名容器被重建、UID/GID、挂载模式改变，旧 key 仍可能命中新映射，使用管理员没确认过的新身份修复。fix 还为正常挂载建 key，未核对其是否曾作为候选返回。
- 修改：采用服务器保存、有期限的扫描/计划记录，绑定 container ID、目标身份、挂载目的地/模式、路径对象信息和修改动作；执行前重查，变化返回 `stale_plan`，要求重新预览。hash 不是用户授权或扫描存在的证明。
- 验收：同名替换容器、改 user、改 RW、目录重建、过期计划和手工构造未预览 key 均不会执行旧计划。

### SAFE-06 P1 对整个目录树清 ACL 和改属主，超出最小修复

- 状态：设计问题，代码确认；现有确认框确实已提示清 ACL，不能写成“完全未告知”。

- 问题：一个子文件不可访问也会导致全树清 access/default ACL、chown。由 NAS 用户、SMB、其他宿主机服务共同使用的目录，不一定在 Docker 挂载计数中表现为共享；混合属主可能是应用设计。当前没有元数据快照或恢复能力。

## 5 扫描和权限判断

### SCAN-01 P1 异常证据丢失，截图不能定位问题

- 状态：代码确认，与用户截图直接对应。
- 位置：第 288–314 行。
- 问题：`bad_any` 保存了第一个不满足要求的路径，输出却只包含根目录属主和模式；未区分缺读、写、进入权限，也没单独证明 ACL 是原因。
- 修改：输出受限数量的异常相对路径、类型、owner/mode、缺少操作、检测方式和错误；区分诊断证据与推测。不把一个模式显示值当作全树状态。
- 验收：根目录 `999:999/700`、子文件不可读的样本显示具体子文件；全树可访问时不能只因根目录 `700` 报错。

用户截图的正确解释：在普通 POSIX DAC/ACL、身份无映射的前提下，UID 999 是该目录所有者且模式 `700`，其根目录所有者权限已是 rwx；ACL mask 不会额外削减 owner entry。仍可能存在子对象、路径环境或其他限制。不能把“根目录 ACL 拒绝”直接认定为截图根因。[POSIX ACL 说明](https://www.man7.org/linux/man-pages/man5/acl.5.html)

### SCAN-02 P1 将 RW=true 推导成所有文件都必须可写

- 状态：代码确认。
- 位置：第 269–279 行。
- 问题：要求读写挂载内所有文件 rw、所有目录 rwx。合法只读配置、证书、混合用途目录会被标成问题；又凭目标路径含 static/assets/public 等名字放宽要求，可能漏掉真实写入需求。`extensions` 名字还影响推荐。
- 修改：分离挂载能力和应用需求，默认只陈述检测到的能力不足，只有明确需求才能判定阻断。删除无法说明依据的目录名猜测，或作为可见、可配置的建议规则。
- 验收：读写挂载中的合法只读文件不自动等于启动故障；只读挂载正常；名字相同的不同业务目录不获得不同的隐式权限结论。[Docker bind mount 说明](https://docs.docker.com/engine/storage/bind-mounts/)

### SCAN-03 P1 宿主机路径探测不等于容器路径探测

- 状态：代码确认；具体误判样本待实机复现。
- 位置：第 288–291 行。
- 问题：宿主机身份访问 `/volX/share/project/data` 需要经过宿主机上层路径；容器可能直接在 `/data` 访问挂载对象。容器目标路径的父目录、覆盖挂载、链接解析环境又可能不同。
- 修改：区分 host simulation 与 container-context probe，报告各自范围。对运行容器可在确认实际工作身份后使用容器内只读探测，但不能依赖容器一定有 shell/find/id，也不能把 exec 默认身份视作实际进程身份。宿主机探测受父路径阻断时应单独标注。
- 验收：宿主机父目录无 x、挂载对象本身可访问的样本，与容器内结果对照；不得为让宿主机模拟成功而放宽 NAS 上层目录。

### SCAN-04 P1 清空补充组可能造成误报

- 状态：代码确认。
- 位置：第 288 行 `--clear-groups`；`get_container_identity` 只返回 UID:GID。
- 问题：容器进程可能依靠补充组获得访问权限，当前模拟丢失这些组；文档将结果描述为实际完整权限判断过强。

## 11 建议的新数据模型

这是建议契约，不是当前已有接口。字段可以精简，但必须保留身份来源、检测可信度、证据、可执行性及过期检测，不能继续用一个 status 同时承载所有含义。

```json
{
  "scanId": "server-issued-id",
  "createdAt": "ISO-8601",
  "complete": true,
  "warnings": [],
  "containers": [
    {
      "id": "full-container-id",
      "name": "example",
      "state": "running",
      "identity": {
        "source": "observed-process",
        "confidence": "verified",
        "containerUid": 999,
        "containerGid": 999,
        "hostUid": 999,
        "hostGid": 999,
        "supplementaryGroups": [],
        "mappingVerified": true
      },
      "mounts": [
        {
          "id": "opaque-mount-id",
          "source": "/vol1/project/db",
          "target": "/data",
          "rw": true,
          "device": "sample-device",
          "inode": "sample-inode",

          "conflicts": [],
          "evidence": [
            {
              "relativePath": "subdir/file",
              "type": "file",
              "owner": "999:999",
              "mode": "000",
              "missing": ["read"],
              "errorCode": "EACCES"
            }
          ]
        }
      ]
    }
  ]

```

规则：示例 evidence 字段必须来自实际采集；如果工具只返回 false 而没有 errno，就不能编造 EACCES。`canPlanRepair` 不等于已批准执行；`verified` 只用于确实完成的检查。

建议访问状态：`accessible / permission_denied / requirement_unknown / identity_unknown / unverified / scan_error / missing / not_directory`。建议安全状态：`eligible / protected / shared_overlap / nested_mount / stale / unsupported`。UI 可做简化映射，后端保留原始细节。

## 14 下一位 AI 的完成标准

- 为上文每个 ID 标注：已修复、已证伪、延期及原因、待设备验证；附变更文件和证据，不能仅回复“全部完成”。
- P0 条目的触发条件和有效防线有证据；未知安装权限或网关行为未核实前，不宣称已解决全部越权风险。
- 扫描结论可解释，未检测与正常分开；截图类问题能定位到具体对象或检测失败原因。
- UI 选中项、服务器计划、实际执行项一致；修复结果逐项保留，部分完成和中断可追溯。
- 真实 Linux 权限样本通过；目标飞牛集成验证的范围与结果明确；不能用 Windows Mock 代替内核权限验收。
- 新版本号、changelog、README、页面和安装向导一致；构建产物含最终修改，并记录哈希与兼容矩阵。
- 交付前再次确认没有对用户真实 NAS 文件执行未经任务授权的权限修改，也没有自动重启业务容器或发布到外部服务。

## 15 查证来源

以下外部资料用于解释通用机制，不证明目标 NAS 的具体配置。平台专有字段以查证后的官方资料和实机结果为准。

- [Docker Bind mounts](https://docs.docker.com/engine/storage/bind-mounts/)：源/目标路径、读写与只读挂载、递归挂载机制。
- [Docker Running containers](https://docs.docker.com/engine/containers/run/)：用户、补充组、capability 配置。
- [Docker exec](https://docs.docker.com/reference/cli/docker/container/exec/)：新命令执行与身份选项；并非读取已有业务进程身份。
- [Docker user namespace](https://docs.docker.com/engine/security/userns-remap/)：容器与宿主机 UID/GID 的映射。
- [POSIX ACL 手册](https://www.man7.org/linux/man-pages/man5/acl.5.html)：owner entry、mask、组访问与 default ACL。
- [GNU Coreutils 手册](https://www.gnu.org/software/coreutils/manual/coreutils.html)：递归属性修改及符号链接策略。目标系统工具版本仍需验证。
- [Node.js Child process](https://nodejs.org/api/child_process.html)：execFile、超时、缓冲与子进程生命周期。实现应进一步按 Node22 文档和实际行为核实。
- [飞牛开发指南](https://developer.fnnas.com/docs/guide/)：本次无法通过网页工具读取，不作为已核实平台规则引用。

本报告不把扫描到的不满足条件直接等同于容器启动失败，也不承诺修改属主和 mode 位可以解决所有 Docker 运行故障。
