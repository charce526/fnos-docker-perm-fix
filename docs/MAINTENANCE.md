# Docker权限修复维护与设备验收

当前版本：1.3.0。维护者：[charce526](https://github.com/charce526)。

## 安装与升级

构建机不需要连接 NAS。使用飞牛应用中心手动安装 `release/docker-perm-fix-1.3.0.fpk`。root 应用的上架资格、最低系统版本及应用中心行为须按目标平台确认；本项目没有将本地参考文档当成上架授权。

从 1.0.0 升级前，先在应用中心停止旧版并确认没有旧版修复任务。旧版只有普通 PID 文件，不能把它视为新控制器已验证的 PID 身份。保留业务备份和旧日志。升级和卸载脚本不删除用户挂载目录或运行元数据；由应用中心的标准安装流程管理数据保留选项，需设备验收。

1.1.0 以 root 运行，通过仅限本机的 Unix Socket 接入网关。包内代码模式统一 0644、目录和生命周期脚本 0755，uid/gid 为 0；1.1.2 在安装和启动时先将本应用 target/server、target/ui 代码及 target 本目录设为 root 所有（目录及脚本 0755、普通文件 0644），然后检查本应用代码；不再对 NAS 卷、@appcenter 等平台父目录强制 root 模式，也不修改这些父目录，运行数据目录使用 0700，元数据文件使用 0600。1.1.1 起，安装预检和启动会通过文件描述符将可信 TRIM_PKGVAR 本目录初始化为 root:root 0700，以适配飞牛分配的应用 UID 和继承权限；不递归更改其中内容，也不操作业务挂载目录。

## 网关 Socket

默认 `app.sock` 为 root:root 0600。**必须在目标飞牛设备核实网关连接身份**；若网关不是 root 且需要专用组访问，在 `${TRIM_PKGETC}/runtime.json` 配置已经核实的数字组 ID，例如：

```json
{"gatewayGid":1234}
```

1234 仅为占位示例，不能直接照抄。该文件必须 root:root 0600；服务会把 Socket 设为 root:指定组 0660。该组不得包含普通 NAS 用户。不要把 Socket 改为 0666，也不要把安装目录改为其他用户可写。配置后在应用中心重启，并分别验证管理员和普通用户经网关的访问行为。

1.1.3 起，界面通过 X-App-Origin 传递浏览器公开来源，CSRF 令牌绑定此来源及当前管理员。写请求校验 Origin 与令牌绑定来源，不与网关内部 Host 比较，兼容 IP、域名和 HTTPS 代理入口；仍拒绝跨站请求和无效令牌。网关是否覆盖客户端自带 X-Trim 头、入口是否只对管理员显示，均须设备测试。

## 运行要求和限制

- x86_64 或 ARM64 Linux、Node.js 22（应用依赖 `nodejs_v22`）、Linux root、宿主机 Docker CLI/daemon（固定本机 unix:///var/run/docker.sock，不继承远程 context）、`/proc` 和安全描述符操作。
- getfacl 用于修复前记录权限和 ACL 信息并验证 ACL 保留；缺失时保留扫描，禁用修复。调整普通文件属主还要求 getcap 检查，缺少工具或文件存在 capability 时拒绝该动作，避免 chown 静默清除文件能力。不再使用 setpriv、setfacl 或递归 chown/chmod 命令。
- 自动修复只支持已验证的本地可写 ext4/btrfs/xfs；网络盘、未知文件系统、挂载别名、链接/特殊对象、硬链接文件、系统及 NAS 管理子树保守拒绝。修改范围是 Docker 绑定挂载的挂载路径或普通文件，不递归子文件；挂载路径内部的子挂载不进入修改范围。
- userns/rootless 和多工作身份暂不自动修复。root 进程带 `CAP_DAC_OVERRIDE` 时报告权限不受限；root 但缺少该能力时显示未检测。停止且没有完整数字 UID:GID 声明时不推断身份。
- 计划执行时不需要停止容器。修复期间会重新核对容器配置、挂载和运行身份；修复完成后提示用户重启容器核对。目录继续被其他宿主机程序修改时应先协调维护窗口。
- 描述符与快照能阻断已识别的路径替换和链接风险，但文件系统操作不是原子事务，不能保证防止有特权的外部进程同时改变所有挂载、硬链接或元数据。没有独占维护条件时不要执行大范围属主调整。
- 修改记录不包含文件内容或全部 xattr，不是数据备份。更改普通文件属主前会检查并拒绝已有文件 capability；本版本仍不承诺备份或自动恢复全部 xattr 和其他内核属性。

## 日志与故障定位

位置均相对于 `${TRIM_PKGVAR}`：`app.log` 是服务输出，`audit.log` 是结构化审计，`jobs/<UUID>.json` 是任务和结果，`jobs/<UUID>.journal.jsonl` 是修改快照及挂载路径变更日志。`app.pid.json` 记录 PID、进程启动时间和服务路径；`control.lock` 与 `execution.lock` 分别管理生命周期和任务互斥。

遇到挂载路径属主和 700 均正确的告警，先展开该路径的诊断与缺少操作。宿主机源路径上层目录不再纳入挂载路径模拟检查，不要为了消除告警去放宽上层共享权限。读写挂载里的只读配置并不必然需要修复，使用明确的业务需求和容器日志核对。

任务超时、应用停止、磁盘故障或客户端网络中断后，先恢复查看任务，再核对 journal。`before` 已写而没有 `after` 的对象，其实际执行结果不确定，应在维护窗口核对该对象的当前 uid/gid/mode/ACL，不要直接重放整批或假定已回滚。日志中的 ACL 和原始身份可供管理员逐对象恢复；路径和 inode 已变化时先停止恢复并核对对象，不把旧路径盲目传给递归恢复命令。

锁文件保留表示可能仍有执行者。应核对记录的 PID、启动时间和进程命令，确认对应服务和 worker 已退出后再处理残留；新任务仅自动清理由启动时间证明两个进程都已结束的锁。不要凭 `kill -0` 或仅见相同 PID 就杀进程。

## 本地开发与验证

生产缺少 Socket 配置不会退回 TCP。开发必须显式设置 `DEV_MODE=1`、绝对路径 `VAR_DIR`、64 位随机十六进制 `DEV_TOKEN`，只绑定 127.0.0.1。开发页面在 localhost 显示独立令牌输入；令牌不应复用 NAS 凭据。Windows 仅用于界面、契约、策略和构建测试，扫描/修复明确拒绝执行。

```powershell
node --test tests/*.test.cjs
node scripts/build.cjs --offline
```

在线构建去掉 --offline。构建使用独立暂存目录和 `npm ci --omit=dev --ignore-scripts`，fnpack 1.2.3 生成包后规范 Unix 权限并更新 app.tgz 校验和，检查关键源码和依赖后原子替换发布包。依赖来自锁文件指定的 registry 地址，离线构建要求已有 npm 缓存。必要时设置 `NPM_CLI`/`FNPACK` 为受信工具的绝对路径。

在**隔离 Linux root 测试环境**中，显式开启真实权限测试：

```bash
RUN_LINUX_PERMISSION_TESTS=1 node --test tests/linux-permissions.test.cjs
```

该套件仅创建和修改自己生成的 `perm-fix-linux-*` 临时目录，覆盖 owner 700、子文件 000、补充组、文件描述符修改和链接拒绝。不得用生产数据目录替代样本。

浏览器回归：`scripts/browser-check.cjs` 使用可用的 Playwright 和 Chromium，设置 `PLAYWRIGHT_MODULE`、`CHROMIUM_PATH` 后运行。它只提供本地假 API；截图和结果存入 `logs/browser/`。旧的 `audit-review.cjs` 和 `audit-engine-probes.sh` 仅为 1.0.0 取证，不能用作 1.1.0 验收。

## 1.1.4 扫描界面与路径规则修正

扫描不再要求选择读取或读写模式：自动检查挂载路径的读、写、进入能力；目录不遍历子项，普通文件只检查文件本身。Docker 只读挂载不要求写入。子文件不可写不再产生整树未完成状态。系统或共享路径是否允许自动修改与权限结果分开显示。

删除“路径任意层以 @ 开头就保护”的错误规则。正常 @appshare、@appdata 下的项目数据及自定义 @ 文件夹不再仅因名称被拦截；NAS 卷根、管理目录根、应用程序/配置子树、实际 Docker 引擎内部目录及本工具目录仍保护。Docker 存储根与项目共用 NAS 父目录时，只禁止修改存储根和具体引擎内部目录，不扩大到所有项目。受保护目录也显示根目录访问检查，并给出具体禁止修改的路径原因；不递归扫描系统目录。旧版扫描记录不自动恢复为新结果，更新后重新扫描。

## 1.1.5 身份识别修正

root、多 UID:GID、不同补充组及能力集合不再统一归为身份未知。界面展示已观察到的身份及启动用户配置，并单独说明无法进行访问模拟的原因；这些结果不自动修复。删除 cgroup 路径含完整 ID 的格式限制，改用两次 Docker 进程列表与 /proc 启动时间复核归属。仅运行身份满足模拟条件或已停止容器提供完整非零数字声明时进行检查。扫描判断版本提升为 3，升级后重新扫描。

本次仅运行身份模块的 13 项定向检查、修改脚本的语法及打包校验，未重跑整套测试，也未连接 NAS 验证。

## 1.2.1 挂载路径范围与未检测状态

- 扫描只处理 Docker `Mounts` 明确返回的 bind 源路径：目录检查目录本身，普通文件检查文件本身；不递归子文件，也不因无关挂载读取失败阻塞整个项目。
- 停止容器、无法模拟身份和本次未执行访问检查统一显示“未检测”。未检测不归为正常或异常；停止容器只有在完整非零数字 UID:GID 声明时才能进入修复，并要求管理员在确认窗口核对。
- 修复只保留“对齐容器身份”：将挂载路径 UID:GID 调整为容器身份，再补访问权限；ACL 保留。
- 勾选可修复项后，批量修复按钮只依据选中项是否有效、是否超过 100 项以及任务是否执行中来决定，不再被旧的全轮扫描 `complete` 标志禁用。
- 扫描 `checkVersion` 提升为 4；旧扫描结果不会自动恢复，升级后需重新扫描。

## 1.2.2 修复方式和顺序简化

- 修复接口只保留 `align-container-identity`，不再提供“仅补当前属主”和“调整属主”两种方式；执行语义是先对齐挂载路径 UID/GID，再补访问权限。
- root 容器进程带 `CAP_DAC_OVERRIDE` 时，挂载权限显示为正常，不再误报“未检测”；root 但缺少该能力时仍显示未检测。
- 界面身份只显示“容器身份：UID:GID”或“容器身份：root”，删除补充组和重复来源说明。
- 左侧项目树与右侧检查结果统一按项目名、容器名和挂载路径排序，移除“关注程度”排序。

## 1.2.3 修复确认简化
