# Docker权限修复

![应用图标](app/ICON.PNG)

检查飞牛 fnOS 中 Docker 项目明确映射到宿主机的目录或文件权限，定位挂载路径访问异常，并在预览后批量执行权限修复。

**版本：1.3.0**

[下载安装包](release/docker-perm-fix-1.3.0.fpk) · [维护文档](docs/MAINTENANCE.md) · [接口说明](docs/API.md)

## 功能

- **项目导航**：左侧按 Compose 项目归组，显示项目、容器状态，点击直接跳转；独立容器单独列出。
- **挂载路径检查**：只检查 Docker 明确映射的挂载路径；目录检查目录本身，文件检查文件本身，不遍历子文件。
- **清晰结果**：统一为正常、需关注、未检测、检测失败四类；停止容器或无法模拟身份时明确显示“未检测”。
- **批量修复**：勾选多个可修复项后生成一个批量计划，列出路径和修改前后的权限，确认后执行，保留 ACL 与操作记录。
- **集中帮助**：右上角“帮助”解释 Permission denied 的成因、检查原理、修复方式和应用操作。

## 为什么 Docker 会 Permission denied

Linux 的普通权限由属主 UID、属组 GID 和权限位决定；飞牛 NAS 还会用 POSIX ACL 记录用户、用户组、掩码和默认 ACL，共享目录通常通过继承 ACL 控制访问。Docker 绑定挂载只是把 NAS 目录映射到容器路径，不会复制目录，也不会重写这些权限。

容器进程仍有一个宿主机视角的 UID/GID。容器内访问挂载路径时，内核按 NAS 上的真实文件判断：先看属主和权限位，再看 POSIX ACL、补充组和用户映射。Docker 镜像经常使用固定 UID，如 999、1000、1001；飞牛共享目录又可能由管理员账户或继承 ACL 管理。两者不一致，而容器进程不在允许访问的用户组里时，读取、写入或进入目录就会返回 Permission denied。

常见场景包括：镜像固定 UID/GID 与飞牛用户或应用 UID 不一致；Compose 设置的 user 与目录属主不同；共享目录的 ACL 掩码或拒绝项没有覆盖容器身份；目录权限是 700/750，其他身份无法进入；只读挂载仍尝试写入；用户映射或 rootless 导致容器内身份与宿主机 UID 不同。属主不同不一定会失败，关键取决于容器实际需要读、写还是进入。

## 安装与使用

需要飞牛 fnOS 1.2.0 及以上、Docker 和 `nodejs_v22`。应用以 root 运行，修复需宿主机提供 `getfacl`；调整普通文件属主还需 `getcap`。

1. 在飞牛应用中心手动安装 [1.3.0 安装包](release/docker-perm-fix-1.3.0.fpk)，按安装向导输入英文大写 `YES`。
2. 通过飞牛应用入口打开，点击“开始扫描”。左侧目录树列出 Docker 项目和容器，右侧显示检查结果。
3. 点击项目或容器跳转；点击顶部“正常 / 需关注 / 未检测 / 检测失败”状态卡筛选列表，再次点击同一状态卡恢复全部状态。
4. 展开“查看诊断与范围”，确认路径、容器身份、当前属主和受限操作。
5. 勾选一个或多个可修复项，点击“批量修复选中项”预览计划并确认执行。
6. 修复结果显示在“检查与修复”下方，可点击“收起”。请重启对应容器并结合业务日志确认效果。
7. 需要时重新扫描验证最新权限；“更多操作”支持导出诊断和查看审计。

修复只有一种方式：把挂载路径对齐到容器 UID/GID，再补访问权限；应用不会自动停止或启动容器。容器可以直接修复，修复后请重启容器查看效果。容器以 root 运行且具备文件访问能力时，会显示“权限不受限”。

## 工作原理

应用通过 Docker inspect 获取绑定挂载路径和容器配置，从宿主机 `/proc` 读取容器工作进程的 UID/GID、补充组和身份映射，并以该身份模拟访问挂载路径。它判断的是挂载路径在已检查范围内的读、写、进入能力，不代表容器内全部运行环境。

无法核实身份、容器已停止或本次未执行访问检查时显示“未检测”。未检测不代表正常，也不代表异常；没有绑定挂载的容器也计入这个状态。

## 状态说明

| 状态 | 含义 |
| --- | --- |
| 正常 | 挂载路径在已检查范围内访问通过；属主不同本身不是权限错误 |
| 需关注 | 挂载路径存在访问限制或路径问题，需核对具体原因 |
| 未检测 | 容器已停止、无法可靠识别身份或本次未执行访问检查；既不代表正常，也不代表异常 |
| 检测失败 | 检查执行发生错误，详情中保留原因 |

左侧项目和容器显示其中最需要关注的状态。顶部状态卡统计挂载路径；“未检测”还会计入没有绑定挂载的容器，点击状态卡可按对应状态筛选。只读配置不可写可能正常，检测结果不能直接证明容器启动失败的原因。

每个挂载路径的诊断信息会显示宿主目录或宿主文件的属主和权限；普通文件绑定挂载显示为“宿主文件”。

## 检查与修复边界

工具只检查 Docker 绑定挂载（bind mount）的挂载路径或普通文件，命名卷不在本工具范围内，也不递归处理每个子文件。检查以容器进程的数值身份模拟访问；界面只显示“容器身份”。结果不等同于容器内全部运行环境；root、多用户或用户映射等限制会明确说明。

系统目录、Docker 引擎内部目录、共享或重叠路径、链接、硬链接文件及不支持的文件系统不自动修复。不设置 777、不修改 Compose、不清除 ACL。修改记录不包含文件内容，不是业务数据备份，也不提供原子回滚。修复前应安排维护窗口并保留业务备份。

## 构建与检查

离线构建使用锁定依赖，要求本机 npm 缓存已备齐：

```powershell
node scripts/build.cjs --offline
```

安装包输出至 `release/`，包含 Node 服务源码与 Express 依赖。构建会校验版本、运行文件、应用图标、归档权限和嵌套校验和。在线构建可去掉 `--offline`。

左侧目录树和右侧结果都使用项目名、容器名与挂载路径的自然顺序，目录树顺序不会再因“关注程度”和右侧内容不同。结果区不提供额外排序下拉。实际安装升级、飞牛网关与 x86/ARM 运行仍需设备验收。
